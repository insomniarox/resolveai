The shape

Small on purpose

This is a portfolio system with clear exclusions. It has no accounts, autonomous remediation, background workers, general tool execution, or claim of production reliability.

BOUNDARY 01

One core workflow

Prepared fixtures and unseen runtime JSON both reach investigate_evidence(). That is the architectural center.

BOUNDARY 02

Evidence is privileged

Runbooks can guide reasoning. Only collected Evidence IDs can support the returned diagnosis.

BOUNDARY 03

Failure is not uncertainty

A model abstention becomes inconclusive. A database or provider failure stays a system failure with its own category.

Implementation guide

The ideas behind the implementation

Start here if incident investigation, retrieval, or typed Python is new to you.

What problem does this solve?

An incident report describes an effect, such as failing payment requests. It rarely explains the cause. ResolveAI brings observations and operational guidance together, asks for a possible cause, and returns the observations used to support that explanation. The remediation is a recommendation for a person to review. The application never executes it.

Retrieval-augmented generation, in concrete terms

Retrieval-augmented generation means selecting useful documents before asking a language model to answer. Here, the application turns the incident report and Evidence summaries into a search query, retrieves reference text, and includes that text in the reasoning request. This supplies context at request time. It does not train or update the language model.

The guided reasoner is an exception worth understanding. It still runs retrieval, but its Python rules deliberately ignore the retrieved text. That makes it useful for checking the surrounding workflow. It does not demonstrate that retrieval improves reasoning. Separate retrieval-dependent evaluations address that question.

Validation happens at several different boundaries

Pydantic checks incoming fields and relationships between them. The provider adapter checks whether a structured decision is complete. The shared workflow checks whether citations name collected Evidence. The browser checks the received JSON before rendering. Each check answers a different question, so none makes the others redundant.

Types carry meaning, but have limits

Evidence means an observation supplied to this investigation. RetrievedRunbook means reference knowledge found by search. Hypothesis means a proposal awaiting citation checks. These names let a reader follow what each value is allowed to do. Runtime Evidence is caller-supplied, however. Schema validation cannot prove that an observation happened in the real world.

A small synchronous workflow

The Python call stack expresses the execution order. One function returns before the next begins. The reasoner is a callable passed as an argument, which lets deterministic rules and live adapters share the same workflow. There is no autonomous planning loop, tool dispatch, queue, or retry orchestration.

Implementation guide

How text becomes ranked references

The embedding model and the reasoning model do different jobs. Embeddings produce numbers for search; the reasoner proposes an explanation.

  1. Prepare a whole document

    build_document_embedding_text() joins the title and content as Title: … Content: …. Each document is one retrieval unit. There is no chunk splitter.

  2. Generate a 384-number representation

    FastEmbed runs BAAI/bge-small-en-v1.5 locally. query_embed() embeds search text and passage_embed() embeds documents. _ordinary_python_vector() converts model arrays into Python floats. @cache loads the model once per process; it does not cache every query result.

  3. Send a parameterized vector to PostgreSQL

    _format_vector_for_postgres() requires 384 finite values and formats them for vector(384). Psycopg passes the value as a SQL parameter. Runtime storage generates and validates every document vector before inserting any rows.

  4. Rank by cosine distance

    pgvector's <=> operator computes cosine distance. Smaller distance ranks earlier. The API returns 1 - distance as similarity. IDs break equal-distance ties consistently. This is a relevance score, not the probability that a cause is correct.

-- Core of the runtime-document query; abbreviated.
WHERE runtime_knowledge_documents.scope_id = %s
  AND runtime_knowledge_documents.expires_at > now()
ORDER BY
  runtime_knowledge_documents.embedding <=> query_embedding.value ASC,
  runtime_knowledge_documents.document_id ASC
LIMIT %s

Top-3 applies to each collection separately

The workflow first retrieves up to three stored runbooks. If a runtime scope exists, it separately retrieves up to three documents from that scope. It concatenates runbooks first, then runtime documents for the reasoner. There is no global ranking of all six references, reranker, minimum similarity threshold, or service filter in the semantic SQL. The same query is embedded separately by the two search functions.

Storage and baseline search

runbooks contains 15 synthetic seed records plus explicit operator uploads. Historical evaluations used the original nine records. The setup command embeds rows whose embedding is NULL; semantic search excludes those NULL rows until setup completes. The lexical baseline uses a generated English tsvector, weighted title/content terms, websearch_to_tsquery(), and ts_rank(). Its GIN index supports text search. The schema defines no approximate vector index.

The runtime table uses the composite primary key scope_id, document_id. Two requests can reuse a document ID because their server-generated scopes differ. Expiry and scope restrictions live in the SQL predicate, so out-of-scope documents never enter that query's result list.

Implementation guide

The reasoner boundary

One callable accepts an Incident, an Evidence list, and a list of retrieved references. It returns a Hypothesis or raises an exception.

Dependency injection without a framework

HypothesisGenerator describes the callable shape. investigate_evidence() accepts that callable as an argument. The default is generate_fake_hypothesis(), which adapts the evidence-only rules to the shared three-argument contract. Runtime configuration provides a live callable and safe provider/model metadata in ConfiguredRuntimeReasoner.

Configuration selects the transport

get_runtime_reasoner() reads RESOLVEAI_RUNTIME_PROVIDER, validates openai or openrouter, and requires the matching environment key. The configured model IDs are gpt-5.6-luna and openai/gpt-5.6-luna. These are repository settings. There is no caller model selector or automatic fallback.

Build the model input, parse its decision

build_openai_reasoning_input() serializes the complete incident, Evidence, and runbooks to JSON. It adds retrieved_knowledge_documents only when nonempty to preserve the frozen benchmark input shape. The runtime system instructions identify documents as untrusted content and prohibit treating them as instructions or citing them as observations.

_generate_hypothesis() calls client.responses.parse() with the selected decision schema, medium reasoning effort, and a 4,000 output-token limit. Client construction sets a 30-second timeout and zero SDK retries. That timeout is for the provider call; embedding, database operations, cleanup, and snapshot storage add their own time to the HTTP request.

DecisionRequired relationshipAdapter result
diagnosedCause label, explanation, confidence, and remediation are present; citation list is nonempty. Confidence is 0–1.Creates an unverified Hypothesis.
inconclusiveAll diagnosis fields are null and the citation list is empty.Raises InsufficientEvidenceError, which the shared workflow handles normally.

What this boundary cannot establish. Structured parsing checks shape and coherence. Citation verification checks ID membership. Neither proves that a cited observation entails the explanation, calibrates confidence, or guarantees that prompt injection cannot influence the prose. A person still reviews the proposed cause and action.

Trust model

Three types, three levels of authority

The project gets safer because it models these ideas separately. Collapsing them into a generic document type would erase the most important rule.

Evidence

Observed incident facts

Logs, deployments, and normalized runtime observations. Each item has a stable ID and may support a diagnosis.

Authority: citable. The verifier accepts only IDs found in this collection.

Retrieved reference knowledge

Helpful context, not proof

Frozen runbooks and request-scoped documents. Their score measures embedding similarity to the query.

Authority: informative. A high score is neither confidence nor causal support.

Hypothesis

Unverified model output

A root cause, confidence, remediation, and proposed Evidence citations. It is not yet a diagnosis.

Authority: provisional. Application code must promote it after citation checks.

PATTERN 03

Make output states coherent in the schema

A reasoner decision cannot be half-diagnosed. Inconclusive means empty diagnosis fields and no citations. Diagnosed means every field and at least one citation.

Why this beats cleanup code. Invalid combinations fail at the model boundary. Downstream code receives one of two complete states.

PATTERN 05

Use bearer capabilities for ownerless snapshots

The caller receives a random token once. PostgreSQL keeps only its SHA-256 digest. Read and delete require both the UUID and token.

Why it fits. The project needs two short-lived comparable runs, not identity, accounts, sessions, or a sharing system.

Design decisions

Design choices and their tradeoffs

These choices fit the current scale. A good decision can expire when the load, team, or product promise changes.

01 Plain synchronous Python

The operation is one bounded sequence and the API permits one live call per process.

Chosen because

Call order, errors, and cleanup remain visible in one function.

Not LangGraph or a queue

No tool loop, checkpoint, job polling, or recovery workflow exists yet.

02 Semantic Top-3 in PostgreSQL

The frozen benchmark improved from 5/18 lexical Top-1 to 16/18 semantic Top-1.

Chosen because

pgvector keeps retrieval beside the stored corpus with deterministic tie-breaking.

Not a vector service

Nine runbooks and at most five runtime documents do not justify another system.

03 Open runtime labels

Unseen incidents should not be forced into the six-label frozen benchmark taxonomy.

Chosen because

Bounded snake_case preserves causes outside the original synthetic set.

Not an equality key

Live runs produced sound prose with unstable label wording and 0/9 exact-label accuracy.

04 One configured provider

The server selects OpenAI or OpenRouter and exposes only safe model metadata.

Chosen because

Costs, keys, timeouts, and output behavior stay operator-controlled.

Not automatic fallback

A fallback would make provenance and repeated-run comparison harder to explain.

05 Immutable one-hour snapshots

A saved run captures input, retrieval, output, settings, timestamps, and stable failures.

Chosen because

Two attempts can be compared without building user storage.

Not CRUD history

No owner, list, or update route means far less privacy and authorization machinery.

06 Honest inconclusive outcomes

InsufficientEvidenceError is caught as a normal reasoning branch.

Chosen because

Uncertainty is information and should return the collected Evidence and references.

Not a generic exception

Provider, validation, citation, and storage failures require different operator responses.

Implementation guide

Execution, cleanup, and saved provenance

The transient and saved endpoints wrap the same execution function. Saving starts a new investigation and records that attempt.

The runtime wrapper owns temporary resources

execute_runtime_investigation() converts the bundle, records a UTC start time, and starts a monotonic perf_counter() for elapsed duration. With documents, it allocates a UUID and sets expiry to start time plus 15 minutes. store_runtime_knowledge_documents() embeds the entire set, then uses a Psycopg transaction to insert all rows or roll them all back.

The inner capture_retrieval() function copies the ordered references passed to the live reasoner. This closure preserves the references if reasoning later fails. If retrieval fails before the callable runs, it has no captured references, even if an earlier search completed.

The finally block attempts scope deletion on success and failure, including a failed store. A cleanup error is logged and does not replace the original investigation outcome. Scope filtering isolates requests immediately; expiry later excludes stale rows, and future ingestion purges them. There is no scheduled deletion worker.

Known failures have a safe, reusable vocabulary

_failure_code() maps known exceptions to five categories. RuntimeInvestigationFailure holds the category, copied metadata and references, timestamps, and duration. Python exception chaining retains the underlying exception for debugging. Unknown exceptions propagate. In particular, frozen-runbook PostgreSQL failures are not all translated into the runtime-knowledge category.

A saved run records a result or a known failure

snapshot_from_attempt() copies the submitted bundle and successful result. An inconclusive result is still a completed attempt. snapshot_from_failure() keeps the bundle, captured references, and safe failure code without raw provider exception details. The snapshot validator requires exactly one result or failure, matching incident IDs for results, and completion at or after the start time.

Execution metadata records application, prompt, and output-schema versions; retrieval strategy and limit; embedding model; reasoning effort; output-token budget; and timeout. This explains differences between runs, but does not guarantee deterministic replay of a live provider response.

Possession of a token grants access

create_investigation_run() generates a UUID and secrets.token_urlsafe(32) capability. PostgreSQL stores its SHA-256 digest and the JSONB snapshot. The creation response returns the plaintext token once. Read and delete requests send it in Authorization: Bearer …, never in the URL.

The SQL requires the ID, matching digest, and an unexpired row. The API gives missing, unauthorized, deleted, and expired runs the same 404 response. There is no account, list route, or update route. One-hour expiry begins when the snapshot is stored. Expired rows are purged opportunistically during run operations; physical deletion at an exact deadline is not guaranteed.

Saved data includes document text. Deleting temporary retrieval rows does not remove documents copied into an explicitly saved bundle or its retrieved-reference lists. Those copies follow the saved run's one-hour lifetime. The default transient path creates no investigation snapshot.

Source: runtime_investigation.py, investigation_runs.py.

Admission is separate from execution

Runtime routes check provider configuration and acquire BoundedSemaphore(1) without blocking. A busy process responds with 429. Ordinary runtime routes release the gate in finally; the saved route stores its snapshot after releasing it. Multiple worker processes each have their own semaphore, so this is not a deployment-wide concurrency limit.

Input validation returns 422. Invalid citations and invalid reasoner output map to 502. Provider timeout maps to 504. Known provider availability and runtime-knowledge failures map to 503. Snapshot storage failure also returns 503, without pretending that a run was saved. Unclassified exceptions are allowed to propagate rather than being reported as an inconclusive investigation.

Implementation guide

How the browser keeps the contract

Next.js presents the two investigation modes and forwards same-origin API requests to FastAPI. React owns the current editing and comparison state.

Form and JSON editing share one bundle

RuntimeInvestigationWorkspace owns the bundle, validation messages, request state, current result, and saved comparisons with React state. The editor components update the same bundle. cloneExampleRuntimeBundle() returns an independent initial value. prepareRuntimeBundle() copies the form data and converts local datetime values to timestamps with offsets before submission.

validateRuntimeBundle() returns readable errors. parseRuntimeBundleJson() parses JSON as unknown, validates it, and returns a typed bundle only after checks pass. runtimeDocumentsFromFiles() reads supported local text and Markdown files into document values. It does not upload arbitrary binary files or fetch URLs.

One user action becomes one request

runInvestigation() checks browser form validity, prepares and validates the bundle, and sets state to loading. Transient mode calls investigateRuntimeBundle(). Saved mode calls createRuntimeInvestigationRun(), then fetches the created run with its returned capability before adding it to comparisons. Error handling changes the request state; finally clears the active action.

TypeScript cannot validate network bytes

TypeScript checks code during development. JSON arriving over HTTP can still violate the declared types. requestJson() therefore returns unknown. Nested guards such as isEvidence() and isInvestigationResult() check actual values. The result guard requires no diagnosis for inconclusive status and checks that every supporting citation names returned Evidence for a diagnosed result.

ApiRequestError represents an HTTP failure, including readable FastAPI validation locations. UnexpectedResponseError represents JSON that cannot be parsed or fails the expected response shape. The workspaces display these separately from diagnosed and inconclusive outcomes.

Comparison shows repeatability, not a semantic verdict

The UI holds at most two saved runs for the same incident ID. This is a browser constraint, not a server-wide per-incident quota. Capability tokens stay in component memory; reloading loses that access state. The same incident ID also does not prove the rest of the two submitted bundles are identical.

The comparison component displays raw labels and prose. Its mechanical comparisons include outcome, ordered retrieved references, and supporting citation IDs, sorted before comparison. Different labels do not automatically mean different causes. Deletion calls the protected endpoint and removes the local comparison only after success.

Recommendations

Keep the clarity. Harden only what demand proves.

The current limits are acceptable for a showcase. The next move should preserve the codebase's strongest quality: you can still explain the whole request in one sitting.

Do not "fix" these

  • Keep Evidence separate from reference knowledge. This is the core safety boundary.
  • Keep abstention ordinary. Inconclusive is a useful result, not a red error banner.
  • Keep the single shared workflow. Do not create a runtime-only reasoning pipeline.
  • Keep frozen evaluations outside product imports. Tests should measure behavior without becoming behavior.
  • Keep raw labels out of semantic equality decisions. Compare stable fields and leave causal prose to human review.

Change these when the trigger arrives

  1. P1Add an external concurrency limit before multiple API replicas. The current semaphore allows one provider call per process, not one across the deployment.
  2. P1Add scheduled deletion if retention becomes a promise. Opportunistic purge and expiry protect retrieval, but stale rows can remain physically stored.
  3. P2Move live work to jobs only when request timeouts hurt users. That change brings IDs, polling, cancellation, and worker recovery. Do it as one explicit product step.
  4. P2Generate browser validators when the contract changes often. Manual guards are readable now. Repeated drift would justify schema generation.
  5. P3Add entailment checks only with a measured rubric. Citation existence is mechanical. Causal support needs evaluation data, not another vague model prompt.

Failure and retention boundaries

A provider failure preserves the other result. Shared preparation failure stops both. A request-owned worker retains admission until calls and cleanup finish even if the browser disconnects. Each route makes at most two calls with 30-second SDK timeouts and no retries. This is process-local admission, not a deployment-wide quota. Immediate document deletion can be deferred to expiry and later purge if PostgreSQL cleanup fails.

Results remain transient, with JSON download for review. Editing input marks displayed results stale. The saved-run workflow remains separate. The next open problem is candidate coverage; the user supplies hypotheses in this feature, and automatic extraction has not been validated.

Unresolved conflicts must not be treated as proof. Retrieval still selects up to three runbooks and three attachments independently, without a service filter or minimum similarity threshold. GET /runbooks lists the library. POST /runbooks accepts JSON fields title, service and content, returning 201 with the new record. Server-generated UPLOAD- UUIDs prevent overwriting seeds. Invalid input returns 422; storage failure returns 503. The existing local-workspace access boundary governs writes.

Model cards split input/output tokens and sum returned calls. Failed branches label counts as partial. Provider tokenization, accounting and completed stage counts can differ; higher Jev token totals alone do not establish higher cost or worse quality. The application does not identify the exact cause of a token-count difference.

Jev returns tokens without billed cost. For jev-1.13.0, Estimated cost uses $0.042 per million input tokens with free output, checked on 2026-09-22 against TypeSafe's model documentation. It excludes shared retrieval and embedding work and is not an invoice. Unknown Jev versions receive no estimate. Exported events keep estimated_cost_usd and cost_basis separate from reported_cost_usd; reported cost takes precedence.

An optional Reference answer lets the operator select a candidate or No hypothesis established. Cards show match or mismatch against the answer captured at submission. Failed branches remain unassessed. The browser includes the reference in the result export but never sends it to either model. Editing a candidate clears the reference selection. One match is not an accuracy benchmark, and confidence is not accuracy.

Existing databases need database/init.sql reapplied and the runbook embedding setup command rerun. This preserves uploaded records and unchanged embeddings. Historical nine-runbook scores describe the earlier corpus; seed additions and uploads can change retrieval. Browser smoke testing and live provider evaluation remain manual for this change.
